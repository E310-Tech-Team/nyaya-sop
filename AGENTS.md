# Agent notes: School of Purpose

Expression-of-interest site: React SPA (Vite, installable PWA with a service worker) + Fastify API + PostgreSQL + a background worker (Postgres job queue). Optional applicant accounts, Web Push notifications, and an admin platform at `/admin`. It started as a Figma Make export and is now a standalone project. The Figma tooling has been removed. It runs on one VPS, or with the website on Vercel and `/api` forwarded to the VPS (`docs/DEPLOYMENT.md` §C). Production is https://nyayasop.org: the whole site on one DigitalOcean Droplet, installed with `deploy/install.sh` (06 D-49) and released from `main` by GitHub Actions once the owner's one-time setup is done (D-51, "Releases" below); `www` redirects there through `WWW_REDIRECT` in `deploy/Caddyfile`.

## Before you change things

- Read the docs in `docs/` (01-PRD … 06-Implementation-Plan, DEPLOYMENT). **Keep them current** when you change features, routes, the schema or the stack, especially `05-Backend-Schema.md` and `06-Implementation-Plan.md`.
- `pnpm check` must pass (typecheck + tests + build).

## Commands

- `pnpm dev`: Vite on :5173 + API on :3000 (embedded PGlite database in `.data/pglite`, no setup; test email outbox at `/api/dev/outbox`). No service worker in dev: test PWA behaviour with `pnpm build` + the built server on `localhost`
- `pnpm test`: Vitest. API tests use `createTestContext()` in `server/test-helpers.ts` (in-memory PGlite, the email outbox and a **fake push transport**: tests never reach a real push service or email provider)
- `pnpm typecheck`: app + server, then the service worker (`tsconfig.sw.json`, WebWorker types)
- `pnpm build` / `pnpm start` / `pnpm worker`: production build, server, separate worker
- `pnpm admin create-owner|reset-mfa|reset-password|list`, `pnpm push:keys`. PGlite is single-process: stop `pnpm dev` before running these against `.data/pglite`

## Conventions

- **Form options and validation live in `src/shared/`** and are imported by both the browser and the server. Enum values there must match the Postgres enums in `server/migrations/`. Change both together, via a **new** migration file (never edit an applied one).
- A form option that is withdrawn stays in its enum for the rows that hold it (06 D-54: "Prefer not to say"): keep it in a separate list that labels stored rows (`GENDERS` is what the form offers; `STORED_GENDERS` adds `EARLIER_GENDERS`), refuse it in the shared validation, clear it from saved drafts (`restoreDraft`), and back that with a trigger that only checks new rows and changed values (migration 0011), not a CHECK constraint: even a `NOT VALID` one fails every later update of those rows.
- Server code must not import React/DOM; `src/shared/` must not import Node or DOM APIs.
- Styling: Tailwind v4 utilities; design tokens (`bg-brand`, `text-muted`, `font-display`, …) are defined in `src/index.css` `@theme`. The homepage hero and the reused editorial sections still use the Figma export's arbitrary values.
- Marketing pages (`/`, `/about`, `/programme`, `/journey`, `/faq`): mobile/tablet layout below `xl` (1280px); from 1280px a 1440px frame scaled with CSS `zoom` (`.landing-desktop` for the fixed compositions, `.landing-scale` for fluid sections; `useLandingZoom` sets it). Form pages switch to the side-panel layout at `lg` (1024px).
- Navigation lives in `src/components/marketing/nav.ts`; the header, desktop nav, menu, footer, page intro and apply band in `src/components/marketing/`. The four dedicated pages render inside `MarketingLayout` (a layout route in `src/App.tsx`); the homepage builds its hero header from the same parts. Use `NavLink` for nav items (it sets `aria-current="page"`). The homepage previews keep the ids `about`, `programme`, `journey`, `faq`, so old `/#…` links still work: don't rename them.
- Decorative layers drawn over interactive content (the hero photograph and ring) need `pointer-events-none`.
- The marketing header is sticky (`StickyHeader`). Don't give its ancestors `overflow`, `transform` or `contain` (that breaks `position: sticky`), keep content below `z-40`, and don't add `scroll-padding-top` (focus inside the header then scrolls the page). Offsets come from `--sticky-header-height` via `scroll-margin-top` in `index.css`; change it with the header's height.
- Accessibility: use native inputs (styled), `<label>`/`<fieldset>`, `aria-invalid` + `aria-describedby` for errors, one `<h1 data-page-heading tabIndex={-1}>` per screen (focused on navigation).
- Programme facts shown in more than one place (hero, What to expect, previews, the About/Programme/Journey/FAQ pages, welcome checklist) live in `src/config/programme.ts` (`src/config/programme.test.ts` checks the nav order, FAQ groups/previews and the journey stages). Only confirmed copy: no invented dates, fees, criteria, response times or contact details.
- New marketing sections should be **one responsive tree** (`.landing-gutter` below 1280px, `.landing-scale` + 1440px-frame values from 1280px), not another mobile/desktop pair or fixed composition.
- Motion (docs/04 §6): use the tokens in `src/index.css` `:root`, the `.enter-*` / `.form-enter` classes with `enterStep()`/`enterAfter()`, and `data-reveal` for scroll reveals (`data-reveal-group` + `data-reveal-at` for a section's timeline, `data-reveal-with` for companions, `data-depth` for a photo settling inside its frame). Every entrance must end on the element's own resting style: motion never changes the settled UI. Animate only `opacity`, `translate`, `scale`; put anything that hides or moves content inside `@media (prefers-reduced-motion: no-preference)`; never delay forms, consent or errors. Containers that clip decoration but hold focusable content use `.clip-overflow`, not `overflow-hidden`.
- The homepage hero is the exception to the CSS system: a GSAP timeline in `src/lib/heroMotion.ts` (timings in its `HERO_*` tables, tested). Its moves clear their inline styles as they land, so the settled hero equals the page without motion. An element is animated by GSAP **or** CSS, never both: the hero's CSS extras (glow breathing, desktop scroll drift) run on inner elements. Those two are the only sanctioned loop and scroll-linked motion; a new one needs the same care (pause off-screen, none with reduced motion, attach scroll animations only while scrolled).
- Brand: the logo is the supplied artwork in `design/brand/` (palette, rationale and usage rules in its README). Show it with `BrandLockup` (`on="dark"`: cream lettering, `on="light"`: burgundy) and never redraw, recolour or re-type it. `python3 scripts/brand-assets.py` (Pillow) rebuilds the committed lockups, favicons and app icons from the masters. The `brand`, `cream` and `gold` tokens are the brand palette: use them or their `rgba()` tints, not new near-miss hex values. The footer credit's RCCG Young Adults & Youths emblem is the logo as supplied in `design/brand/partners/`, its white page made transparent by `python3 scripts/partner-logo.py` (needs numpy): never recolour or redraw it, and keep `RCCG_YAYA_EMBLEM` (`src/components/marketing/emblem.ts`) in step with the file (`emblem.test.ts`).
- Photography: never change the homepage hero images. Each supporting editorial placement must use a unique photograph; do not reuse photos across pages or sections (responsive renditions of the same placement are fine; `src/components/landing/imagery.test.ts` checks). Supporting photos are AI-generated (the owner's decision, 2026-09-29): follow `docs/IMAGERY.md` §1 (fictional Nigerian young adults, modest clothing, the women in skirts or dresses rather than trousers; no text, logos or invented RCCG branding), keep masters in `design/imagery/<date>/masters` and build the site files with `python3 scripts/imagery-assets.py`, record each image (prompt, tool, date, placement) in `docs/IMAGERY.md` (§4, or the batch's `prompts.json` plus §6), keep the footer's "About our images" note accurate, and never caption or describe them as real participants or events. Crops use a per-slot `object-position` focus (`JOURNEY_ART` in `JourneySection.tsx`, `PHASE_ART` in `programmePhotos.ts`, classes in `VisionMission`/`Previews`/`Doctrine`). The brand artwork and the Biblical Blueprint paintings are not replaced. An authentic NYAYA photo may still replace one, with written permission recorded; never crop out watermarks.
- Never log request bodies (they contain personal data), push subscriptions (endpoints, keys) or notification content. `server/push.test.ts` checks the logs. Log errors through the Fastify logger (its `err` serializer is `errorForLog`, which drops database `detail`, `where`, queries and parameters) or as codes, never an error's message from SMTP or the database next to personal data.
- **Security patterns (2026-09-30 audit; regression tests are marked "(security audit)"):**
  - Attempt limits are counted **before** the check, in one atomic `UPDATE … RETURNING` (`takeAttempt` / the MFA reservation in `server/auth/staff-routes.ts`): never read a counter, do slow work, then write it back.
  - Work a response must not wait on (so its timing can't reveal anything, e.g. whether an address is staff) goes through `runInBackground()`; tests await `backgroundIdle()` before reading the outbox.
  - Void outstanding link tokens on security events (`voidStaffTokens`, `voidSignInTokens`); pages read link tokens with `useLinkToken()`, which takes them out of the address bar.
  - A device that leaves an account is unlinked (`unlinkSubscription`); rotation only replaces a live subscription and carries its consent.
  - Rules that span rows (the last active owner) are one statement under a row lock, not a check followed by an update.
  - Text that is stored goes through `cleanText()` (no control characters or unpaired surrogates) and is measured with `characters()` (code points, as `char_length`); cut with `truncate()`. Query strings are single-valued (`firstValues`); look up dictionaries with `Object.hasOwn`.
  - CSV cells are all quoted (`csvCell`). The XLSX reader scans with `indexOf` and enforces Excel's limits: no lazy regexes over whole parts.
  - `vercel.json` repeats every security header the server sends, including `Permissions-Policy` (tested). Static files never include dotfiles.
  - A server outside production mode refuses to listen on a network or with a public `SITE_URL` (`assertSafeToListen`); the development outbox answers only its own computer. Keep both when changing configuration or the outbox.

### Accounts, admin, notifications, PWA

- **The admin menu** lives in `src/admin/nav.ts` (`ADMIN_NAV`: order, labels, routes, the permissions that show each item, and its icon; `navFor(role)`), checked by `src/admin/nav.test.ts`. The icons are lucide-react, decorative (`aria-hidden`, the label names the link) and admin-only.
- **Permissions** live in `src/shared/permissions.ts`. Every admin route uses `staffGuard(services, { permission })` (session → active → Origin/CSRF → MFA → permission); the UI's `useCan()` only hides controls. Add a row to the permission matrix test in `server/admin.test.ts` for new areas. Audit sensitive actions with `audit()` (identifiers and field names only).
- **Applicant-facing data:** only `published_status`/`published_message`. Never send notes, the internal `status` or reviewer details to `/api/account/*`.
- State-changing requests from the browser go through `apiRequest(path, { method, csrf: 'staff' | 'applicant', json })` in `src/lib/api.ts`.
- The account (`src/account/`) and admin (`src/admin/`) areas are lazy chunks: don't import them from public pages. They use the kit in `src/components/ui/` (`index.tsx`: `PageHeader` gives the `<h1>`; `when()` always names the time zone), built on the shadcn/ui primitives beside it.
- **shadcn/ui primitives** (`src/components/ui/*.tsx`, `components.json`) are adapted to the brand tokens: no theme variables, no global base styles, the site's focus outline. A new one (`pnpm dlx shadcn@latest add …` or copied by hand) must be adapted the same way: replace `bg-primary`, `text-muted-foreground`, `bg-muted`, `border-input`, `ring-ring` etc. with `brand`, `muted`, `cream`, `line`… (note `text-muted` here is the muted **text** colour), use relative imports, and revert anything the CLI adds to `src/index.css` (CSS variables, `@layer base`, `tw-animate-css`). Entrance motion for popovers/sheets is in `index.css`, keyed on `data-slot` and inside the reduced-motion guard.
- **Public code imports only `src/components/ui/basic.tsx`** from the kit (plain elements with the primitives' classes from `ui/styles.ts`), never a primitive, `lib/utils` or Radix/cva/tailwind-merge/lucide/Recharts: `src/components/ui/bundles.test.ts` enforces it. Recharts, react-day-picker and TanStack Table load only through `src/admin/reports/lazy.tsx`.
- **Service worker:** the caching policy is `src/sw/routing.ts`; change it only with `src/sw/routing.test.ts`. Never cache `/api`, `/admin*`, `/account*` or non-GET requests. Updates must never reload a page by themselves, and the first install taking control of a page (`controllerchange` on a page that loaded uncontrolled) is not an update: never offer one for it (`src/lib/pwa.ts`).
- **Notifications:** links must be in `NOTIFICATION_LINK_PATHS` (`src/shared/platform.ts`). Application updates use the fixed neutral text. Every push shows a notification (no silent pushes). In the browser, call `pushManager.subscribe()` first in the click handler (Safari's user-gesture rule): get the service worker registration beforehand.
- **Jobs:** handlers must be idempotent (delivery is at-least-once). Use dedupe keys and unique constraints, and re-check eligibility right before acting.
- **SQL:** a `$n` parameter used in two places needs an explicit cast in both (`$2::delivery_status`); Postgres deduces one type per parameter. `ON DELETE SET NULL` re-checks table constraints on the child row (see `server/account/delete.ts`).
- **Time:** store UTC; show and enter times in a named zone (default `Africa/Lagos`, "WAT") with `src/shared/time.ts`.
- Install/notification copy must stay honest: feature detection decides what's possible, the user agent only picks instructions; never claim to detect installs universally or to force another browser.

### Releases

- Production is released only by `.github/workflows/ci.yml` (`docs/DEPLOYMENT.md` "Automatic deployment"): a push to `main` runs `check` and `docker` on that commit, then, while the repository variable `AUTO_DEPLOY` is `on`, `deploy` (environment `production`) runs `deploy/ci-deploy.sh` on the Droplet over SSH and checks the live site; a manual run releases a given commit on `main` (rollback). Keep the job ids `check` and `docker` (required status checks), the read-only token, `persist-credentials: false`, and `${{ }}` out of `run:` scripts (pass values through `env:`). The deploy job uses no third-party actions: it is the only one that can read the SSH key.
- Everything merged to `main` is released, and that commit's `deploy/*.sh` run as root on the server: `main` takes only reviewed, checked pull requests.
- Migrations must work with the release before them (the previous worker runs on the migrated database until the new app is healthy, and a rollback runs older code on it): additive first, destructive in a later release. No down-migrations, no database resets.
- `deploy/ci-deploy.sh` runs as root from the checkout it updates: keep everything in functions, with `main "$@"; exit $?` as the last line. It accepts only `deploy <40 lowercase hex>` and writes only to its log (streamed to the caller, so a dropped connection can't stop a release). Neither it nor `install.sh` may print secrets, `.env` or container logs: Actions logs are public, and the app's log holds visitors' addresses. Both take the release lock; `install.sh` keeps its backup-first stop. `server/ci-deploy.test.ts` runs the script against throwaway repositories: extend it with the script.

### Website on Vercel

- `vercel.json` gives the website the server's security headers, cache rules and SPA fallback (`server/app.ts`): change both together; `server/vercel-config.test.ts` compares them. It uses Vercel's routing phases: long caching sits in `hit` (existing files only, so 404s are never cached), and there the **first** matching rule wins, so never let two rules set the same header on a path (the test rejects it).
- `middleware.ts` forwards `/api/*` to `API_ORIGIN`. Vercel runs it as an unbundled Node ES module: its relative imports need the `.js` extension (tested).
- The API trusts `x-edge-client-ip` only with the right `EDGE_PROXY_SECRET` (`server/edge-proxy.ts`, before Fastify logs or rate-limits the request). Never log the secret or put it in a command line.
- Deploy with the CLI only from a clean export of committed files, never from the working folder (it holds `.env`, local databases and dumps; `.vercelignore` is only a backstop).

### Parish directory

- The directory tables (`church_units`, `parishes`, `parish_aliases`, `unit_lineage`, `directory_*`) are written only by `server/directory/store.ts` (imports, from a plan made by the pure `server/directory/plan.ts`), `server/directory/edits.ts` (staff corrections) and `server/directory/api-sync.ts` (the RCCG directory API). Imports go through `pnpm directory` (a dry run unless `--apply`); every apply is one transaction ending with the consistency check, and can be reverted until staff correct the directory. Each staff correction is one transaction: record it in `directory_changes` (`via 'staff'`), mark the field in `staff_fields`, rebuild and check only the parishes it touches (`rebuildCaches`/`checkConsistency` with IDs), audit IDs only.
- Imports keep staff corrections (`staff_fields`; a moved parish's `source_unit_id` is where the source lists it) and report differences as `staff_override`: a new correctable field needs handling in `plan.ts` (`keepUnitCorrections`/`keepParishCorrections`) and a test in `edits.test.ts`.
- `applications.parish_id` is the current parish (the applicant's choice or a staff link); `parish_status`, `parish_name` and `parish_snapshot` are the applicant's answer and never change. Staff set the parish only through `linkApplicationParish` (`server/admin/parish-links.ts`), which resolves or reopens parish reports.
- Reports and the Applicants list share `applicationConditions()` (`server/admin/application-filters.ts`): a new filter goes there so every report count keeps opening the same applications (`server/admin-reports.test.ts` reconciles them). Counts from 1 to 4 go out as `null` ("fewer than 5") to roles without applications.view_all (`maskCount`), in the API, the CSV and the dashboard card.
- **Reports drill-down** (continent → region → province → parish → applications, `reports/Organisation.tsx`): the place is `unit` + `parish` in the URL filters; change it with `PLACE_PARAMS` so anything chosen below the old place is cleared. Every report endpoint calls `scopeProblem()` (unknown IDs 404; a parish outside its unit or a level above it 400): keep new report routes on it. Listings must add up to their parent: applications with no directory parish are the top-level **Unassigned** extra, skipped levels are `direct`/`without` extras, and zero-application units are listed unless `include=applications`. A parish's view shows figures to reports.view but applications only with applications.view_all (and its CSV with applications.export).
- **Reports and analytics** (`src/admin/reports/`): filters live in the URL (`useReportFilters()`, carried between reports and into Applicants); periods are Lagos days (`model.ts`: `todayInLagos`, `dayToDate`/`dateToDay` for the calendar, never `toISOString()` on a picked date); a comparison appears only through `compare()` (a real earlier period; zero or hidden baselines in words). `reportListing()` has three modes (a level, the units under a unit, parishes) plus `extras` so totals add up; its `sort`/`dir` keep status and parish orders from masked roles. Every chart is Recharts via `components/ui/chart.tsx`, unanimated, hidden from assistive technology and paired with its numbers in text. Check all-of permissions with `useCanAll()`, never `useCan(a) && useCan(b)` (hooks can't be conditional).
- Parish review routes use `staffGuard(services, { allOf: [...] })`: they show applicants and change the directory, so any one permission isn't enough. Keep `PARISH_REVIEW` in `src/admin/nav.ts` in step.
- **RCCG directory API** (D-53, [05 §2](docs/05-Backend-Schema.md#directory-api-0010)): once configured (`DIRECTORY_API_ENV` + `DIRECTORY_API_KEY`), it's the directory's only source.
  - **Authority:** `applyPlan` refuses spreadsheets, `revertImport` refuses API syncs, and `assertStaffEditable` closes staff corrections (`apiSuppliesDirectory()`). The spreadsheet path, `DirectorySource` and `plan.ts`, stays for databases without the API.
  - **Identity:** API entries are matched by provider UUID within their namespace (`rccg-org:production|sandbox`; `external_id` = namespace + canonical code), never by name. Never mix the two namespaces: anything that lists or accepts parishes filters by `directoryNamespace(services)`.
  - **The sync:** keep the copy built from immutable releases (`directory_releases`, replayed from the base). Nothing is applied from a partial download, one transaction applies each release, and **only a `retired` change deactivates**. An entry a release doesn't describe usably is kept and reported, never taken as removed.
  - **Freshness:** a stale copy (`isFresh`) makes submissions confirm the parish with `parishByCode`. When the provider can't answer, return 503 `DIRECTORY_UNAVAILABLE`: never accept an unconfirmed parish.
  - **The key:** server-side only, sent only as the bearer header to the fixed addresses in `DIRECTORY_API_BASES`. Never log it, return it, store it or put it in a URL, and never add a `VITE_` or `define` path for it (`server/config.test.ts` checks). Errors are codes (`api_unauthorized`…), and logs carry figures and codes only.
  - **Tests** use `fakeDirectoryApi()` (`server/directory/test-api.ts`), never the real provider. Change the fake only in line with the provider's published contract.
- **Never commit RCCG files or directory reports**: the repository is public, and spreadsheets and CSVs are gitignored. Tests build their own workbooks (`server/directory/test-xlsx.ts`). Only the continent, region, province and parish columns are read: never store the list's attendance figures.
- `CHURCH_LEVELS` in `src/shared/directory.ts` matches the `church_level` enum, in order (`server/directory/store.test.ts` checks). `unitKey()` and `parishKey()` decide how imports recognise entries: changing them needs a migration that recomputes `name_key`.
- Bulk writes pass rows as one JSON parameter through `jsonb_to_recordset`: PGlite doesn't serialise JavaScript arrays of custom enum types.
- Parish search (`server/parishes.ts`) matches `parishes.search_text`, a cache rebuilt with the chain (`rebuildCaches()`): anything that changes names, aliases, provinces or regions must go through the store so it stays current (`checkConsistency()` compares both). Search terms come from `searchTerms()` in `src/shared/directory.ts` (letters and digits only, so they are safe in the LIKE and regex patterns).
- Request logs record the path without the query string (`server/app.ts`): searches carry what people typed and their state. Don't log query parameters elsewhere either.
- A submitted listed parish is re-checked on the server (still active?) and its chain is filled in from the directory, never from names the browser sends. A parish with no continent (`isChainComplete()`) is stored as it is and reported (`details_wrong`), never filled in.
- **Look-alikes** (D-55, [05 §2](docs/05-Backend-Schema.md#look-alikes-0012)): active parishes sharing `unit_id` and `name_key` in one namespace are one choice. Search collapses them to the group's first parish by code (`GROUP_ORDER`, `lookalikeGroup()` in `server/parishes.ts`) with a `lookalikes` count of the whole group, and `total` counts choices. `resolveParish` links that first parish, keeps the group in the snapshot (`lookalikes`) and raises a `lookalike` report, which staff settle in Parish review. Never merge look-alikes by name, and never let the form pick one of them for the applicant.
- **The parish question is compulsory** (D-52): `validateApplication(body, { directory })` refuses a body without `parish` while the directory is on (typed text never counts) and requires `parishName` while it's off. Old `not_provided` rows stay as they are: no submission may store a new one (staff can still clear a typed name in `POST /api/admin/applicants/:id/correct`, e.g. personal data typed in the wrong box). Every apply step calls `useParishQuestion()` (through `RequireStep`), so drafts follow the server's setting; while it's loading or failed, the Personal step can't be completed.
- The parish question in the form (`src/components/ParishPicker.tsx`, `src/lib/parish.ts`): the draft keeps `parishMode` ('directory' while `/api/config` says the directory is on, set by the Personal step) and `parish`. `personalErrors()` and `toPayload()` in `src/state/application.tsx` decide what counts and what is sent: never send `parish` in text mode. A saved listed parish is re-checked at most once per page load, and only when a draft holds one (no requests from other pages). Keep the combobox pattern intact (label, `aria-activedescendant`, Enter never submits while the list is open, one always-mounted `role="status"`), and use `data-focus-invalid` for invalid controls that can't carry `aria-invalid` (buttons).
